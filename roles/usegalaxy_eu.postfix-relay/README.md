# Postfix relay

Deploy with `ansible-playbook -i hosts maintenance.yml`. This runs the full
maintenance playbook; there is no dedicated `postfix.yml`. Deployment settings are in
`group_vars/maintenance.yml`; credentials are supplied through vaulted variables.

## Delivery transports

Postfix uses shared persistent queue storage with independent transport scheduling:

| Message | Transport | Deployment pacing |
| --- | --- | --- |
| Subject matches `postfix_bulk_subject_regex` | `bulk` | 30s delay (~120 messages/hour), concurrency limit 2 |
| Null envelope sender (`<>`, delivery-status notifications) | `dsnrelay` | No rate delay, concurrency limit 2 |
| All other mail, including regular Galaxy email | `smtp` | 8s delay (~450 messages/hour), concurrency limit 2 |

Routing is subject-based: the `header_checks` lookup table (applied by the
`cleanup` service to every message entering the queue) matches the `Subject`
header and hands matches to the paced `bulk` transport with a `FILTER` action.
The `FILTER` action must name the upstream relay explicitly as its next-hop
destination (`FILTER bulk:[relay]:port`): an empty `FILTER` destination does
not fall back to `relayhost` the way transport-map entries do — it would
deliver directly to the recipient domain.
The envelope sender and `From` header are
irrelevant, so campaign mail can use exactly the same address as regular
Galaxy email — the global `email_from`
(`European Galaxy Team <galaxy-no-reply@informatik.uni-freiburg.de>` covers
account activation, password resets, notifications, and campaign mail alike).
Campaign submissions must include the subject tag
(`postfix_bulk_subject_regex`, default `[Galaxy bulk]`); Galaxy's regular
email never carries it. Bounces are returned to the envelope sender, which is
the relay's single upstream account; they are routed to the unpaced
`dsnrelay` transport by the null sender map, not by headers, because bounces
generated by Postfix itself never pass through smtpd.

`header_checks` applies to all mail entering the queue, including locally
submitted mail (`postfix sendmail`) — but regular mail never carries the
campaign subject tag. A
message receives at most one `FILTER` destination; if several patterns
matched, the last one would win, so keep the table to a single pattern.

The queue manager reads transport-specific delays and concurrency limits from
`main.cf`. The custom SMTP delivery services in `master.cf` inherit the upstream
SASL and TLS settings. Log prefixes distinguish `postfix/bulk/smtp` and
`postfix/dsnrelay/smtp` from regular `postfix/smtp` deliveries.

Together the paced transports target approximately 700 single-recipient
deliveries/hour (600 bulk plus 100 regular). Bounces are additional and unpaced.
They share one upstream account: the combined traffic, including bounces, is
still subject to that account's recipient limit and the source host's connection
and authentication limits. A delivery delay is not a strict recipient quota.

## Verification after deployment

On maintenance, inspect the maps (use `hash:` instead of `lmdb:` if that type
was selected, and `regexp:` if the build lacks `pcre:`):

```bash
postmap -q 'Subject: [Galaxy bulk] Updated Terms of Service and Privacy Policy' pcre:/etc/postfix/header_checks
postmap -q 'Subject: Your Galaxy account activation' pcre:/etc/postfix/header_checks
postmap -q '<>' lmdb:/etc/postfix/sender_transport
postconf header_checks smtp_destination_rate_delay bulk_destination_rate_delay dsnrelay_destination_rate_delay
postconf -M bulk/unix dsnrelay/unix
postfix check
```

Expected results: the campaign subject matches with `FILTER
bulk:[{{ postfix_relay_host }}]:{{ postfix_relay_port }}`, the regular
subject does not match (default `smtp`), and the null sender resolves to
`dsnrelay:`.

From sn09, submit several single-recipient test messages carrying the campaign
subject tag, then submit one using Galaxy's regular subject. Check
`/var/log/maillog`: campaign deliveries should be spaced by approximately 30
seconds and regular deliveries by approximately eight seconds. Regular mail should
use its independent transport rather
than wait for the campaign to finish. Confirm `status=sent` and inbox receipt.

Unchanged daily playbook runs do not rebuild the routing database or restart
Postfix. Changes to the sender map, header checks, transport configuration, or
other managed configuration trigger the restart handler. Temporary failures
remain queued for the configured lifetime; permanent SMTP rejections generate
bounces.

## Restart recovery and availability

Accepted mail is stored in Postfix's persistent queue (normally
`/var/spool/postfix`, inspect with `postconf queue_directory`), not just in RAM.
A normal service restart or host reboot preserves queued messages, and Postfix
resumes delivery automatically. The role sets `enabled: true` so the service
starts on boot. This assumes the queue filesystem survives and is available;
disk loss, corruption, or deleting/replacing the spool can lose mail. A restart
does not reset message age or the configured 30-day queue lifetime.
Unlike the queue itself, destination rate-delay timers are in memory and do not
survive a restart or reload. Deliveries can therefore resume immediately, so
restarting repeatedly can undermine the intended pacing.

During downtime, new SMTP submissions can fail. Mail that has not received the
final SMTP acceptance response is still the submitting application's
responsibility; verify Galaxy/Celery retries rather than assuming Postfix can
recover messages it never accepted. If the connection breaks after acceptance
but before the client receives the response, retrying can produce duplicates.
The same SMTP ambiguity exists when forwarding to the upstream relay.

Before production use, test with a controlled SMTP sink and no real campaign:

1. Temporarily make the test upstream unavailable, submit identifiable messages
   through both transports, and record the accepted queue IDs with `postqueue -p`.
2. Restart Postfix and confirm the messages remain queued. In a planned reboot
   test, also verify `systemctl is-enabled postfix` and automatic startup.
3. Restore the test upstream and confirm delivery resumes and the queue drains;
   correlate message IDs and recipients with `status=sent` in the mail log.
4. Test submission while the relay is stopped and confirm the application retries.

With the relay on maintenance, Galaxy email submission depends on maintenance
and the network path to it, although Galaxy's other functions need not stop.
Moving the relay to sn09 removes that extra host dependency for sn09's own
submissions, but Celery workers still depend on the relay host. Such a move needs
coordinated client, trusted-host, firewall, credential, and playbook changes, and
the old queue must be drained or safely migrated before retiring maintenance's
relay. Keep the queue on durable storage and monitor queue age and free space
regardless of placement.
